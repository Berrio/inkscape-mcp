# F02 — Workspace, XML y transacciones

## F02-WP01 (completo, 2026-08-29)

- Objetivo verificable: resolver paths de workspace y demostrar que un enlace o una carrera de reparse point no puede redirigir una publicación fuera de los roots autorizados.
- Prerrequisitos/puertas: F01-WP05 cerrado; ADR-004 y ADR-008 definen el límite TOCTOU residual.
- Interfaces disponibles: `WorkspaceService`, `AtomicFileStore`, `CanonicalPathLocks` y revisiones SHA-256.
- Archivos/artefactos esperados: guardia de publicación, pruebas unitarias de junction/carrera, ADR y este informe.
- Tareas condicionales permitidas (`[-]`/`[w]`): ninguna.
- No-objetivos: helper nativo con handles, sandbox o resistencia total frente a un actor local que altere el filesystem después de la comprobación final.
- Comandos exactos: `npm test -- --run tests/unit/storage.test.ts tests/unit/workspace.test.ts`; `npm run check`.
- Assertions/tolerancias: los roots se congelan al crear el runtime; antes de staging y antes de publicar cada archivo se resuelve de nuevo el parent, que debe continuar bajo el root congelado. Un output final symlink se rechaza.

### Resultado y mini-puerta

- `F02-T05` cerrado. La prueba existente cubre la junction que sale del root al resolver inputs; la nueva prueba cambia la carpeta de salida por una junction hacia un directorio externo después de escribir el temporal. La publicación devuelve conflicto y no aparece `result.png` fuera del workspace.
- `AtomicFileStore` aplica la guardia a commits individuales y en lote cuando el runtime tiene `workspaceRoots`; los stores de prueba/infraestructura sin roots siguen siendo neutrales y no se convierten en una API pública de paths.
- Verificación: las pruebas focalizadas pasaron con 27/27. `npm run check` pasó: formato, lint, TypeScript y 69 archivos de prueba (245 passed, 1 skipped; 246 tests en total). `npm run test:mcp` también pasó contra el binario construido y la instalación local de Inkscape, sin procesos remanentes.
- Archivos: `src/storage/revisions.ts`, `src/storage/index.ts`, `src/server/index.ts`, `tests/unit/storage.test.ts`, `docs/architecture/adr-008-workspace-threat-model.md`, `PLAN_IMPLEMENTACION.md` y este informe.
- Riesgo residual: Node no puede impedir un intercambio que ocurra después del segundo `realpath` y antes del `rename`; se mantiene la exigencia de ACLs de root y el helper handle-based queda en F12.
- El siguiente WP lógico es `F03-WP01`; no se ejecutó en este corte.

- ADR-008 define cliente/documento hostil, ACL requeridas en los roots y el límite TOCTOU de Node sin helper privilegiado.
- `WorkspaceService` crea IDs opacos de roots canónicos y resuelve solo paths relativos seguros.
- Las entradas existentes usan `realpath`; los outputs nuevos validan el parent canónico. Se rechazan absolute, UNC, drive-relative, NUL, ADS y segmentos de traversal.
- La prueba Windows usa una junction de directorio para demostrar que un escape a otro root se rechaza sin requerir el privilegio de crear symlinks de archivo.

### Verificación ejecutada

```powershell
npm run check
```

- 32 pruebas correctas y una integración opcional omitida.
- SVG/SVGZ usan allowlist y sniffing de contenido; el listado recursivo omite links y pagina con cursores ligados al ID de workspace.
- El recheck de carrera antes de commit (`F02-T05`) quedó integrado en `AtomicFileStore` con una guardia de roots congelados y prueba determinista de junction intercambiada.

## F02-WP02 (completo)

- Las exportaciones PNG, PDF y SVG ya congelan el SVG de origen en el staging y
  validan su hash antes y después de la copia; Inkscape no recibe la ruta viva
  del workspace. La copia de dependencias locales y la reescritura de URI
  siguen pendientes en `F02-T24`.
- Antes de congelar la copia, el pipeline rechaza XML/SVG que la política
  `preserve-local` tendría que limpiar; contenido activo y referencias remotas
  no se entregan al proceso nativo.
- Las mutaciones de resize aplican la misma regla antes de volver a parsear el
  XML: un SVG que requiera limpieza se rechaza sin modificar el documento.

- `ScratchManager` crea dirs únicos de job/probe/staging, garantiza limpieza `finally` y recolecta solo dirs propios obsoletos durante arranque.
- `sha256File` calcula revisiones por stream; una mutación interna porta `MutationDocumentRef` y el overwrite exige la revisión actual del destino.
- Locks por rutas canónicas se adquieren en orden léxico, evitando deadlocks entre source y output.
- `AtomicFileStore` escribe y sincroniza un temporal en el mismo directorio, crea backup único al reemplazar y después hace rename; ADR-005 declara los límites crash/Windows de esta operación.
- Las pruebas cubren revisión obsoleta, overwrite sin revisión, backup y dos writers concurrentes.
- `SnapshotStore` guarda documentos y metadata interna por IDs opacos con
  owner, TTL persistente y retención de 100 snapshots por workspace. Al
  restaurar revalida el hash del snapshot y la revisión actual del destino,
  delegando el reemplazo y backup al `AtomicFileStore`.
- `document_snapshot` exige `expectedRevision`, y `document_restore` exige la
  revisión actual, el ID opaco y el mismo workspace owner. La prueba MCP crea,
  restaura y vuelve a redimensionar un A4; no se aceptan snapshots sin revisión
  ni de otro workspace. `npm run check` pasó con 65 pruebas y una omitida, y
  `npm run test:mcp` pasó en stdio moderno y legacy el 2026-08-25.

## F02-WP03 (completo)

- Objetivo verificable: aplicar el ceiling de confianza a los bundles nativos y
  ampliar la sanitización para recursos y CSS externos sin dañar las referencias
  locales permitidas.
- Prerrequisitos/puertas: F02-WP02 cerrado; `sanitizeSvg` y
  `createNativeInputBundle` son las únicas interfaces que se ampliarán.
- Interfaces disponibles (no inventar otras): `SanitizeMode`, `sanitizeSvg`,
  `NativeInputBundle` y la configuración de arranque ya validada.
- Archivos/artefactos esperados: sanitizador, bundle nativo, pruebas de corpus
  y este informe.
- Tareas condicionales permitidas (`[-]`/`[w]`): ninguna.
- No-objetivos: aceptar `trusted` desde una tool, interpretar CSS completo o
  implementar todavía el remapeo integral de IDs/diff semántico.
- Comandos exactos: `npm test -- --run tests/unit/safe-svg.test.ts`
  `tests/unit/storage.test.ts`, `npm run check`.
- Assertions/tolerancias: `strict` permite solo refs fragmentarias; el ceiling
  `strict` convierte la sanitización nativa por defecto a strict y ningún
  bundle nativo recibe contenido que haya requerido limpieza.
- Resultado: T18–T21 completadas. `sanitizeSvg` elimina scripts, eventos,
  `foreignObject` estricto, refs externas y URLs externas en atributos/CSS;
  `createNativeInputBundle` usa el ceiling configurado y nunca eleva a
  `trusted`. `normalizeSvgIds` conserva la primera definición de duplicados,
  normaliza IDs inválidos/opcionalmente faltantes y actualiza `href`, ARIA,
  `url(#...)` en fill/clip/mask/filter/marker y selectores CSS literales o
  escapados conocidos. `summarizeSvgDiff` ofrece conteos e IDs, no markup.

## F02-WP04 (completo)

- Objetivo verificable: publicar previews grandes como capabilities opacas de
  recurso MCP por fragmentos, y garantizar que Inkscape solo consume un árbol
  de inputs local, copiado, con hash y manifest reproducibles.
- Prerrequisitos/puertas: F02-WP03 cerrado; `ArtifactStore`,
  `AtomicFileStore`, `ScratchManager` y el ceiling de sanitización ya existen.
- Interfaces disponibles (no inventar otras): `ArtifactStore`,
  `NativeInputBundle`, `ResourceTemplate`, `AtomicFileStore` y resolver de
  workspace interno.
- Archivos/artefactos esperados: recursos `inkscape://artifact/{id}` y
  `.../chunk/{offset}`, manifest interno del bundle, SVG reescrito y assets
  copiados en staging.
- Tareas condicionales permitidas (`[-]`/`[w]`): ninguna.
- No-objetivos: persistir capabilities al reiniciar el proceso, exponer paths
  locales, aceptar URIs remotas o habilitar que el cliente elija confianza.
- Comandos exactos: `npm test -- --run tests/unit/storage.test.ts`,
  `npm run check`, `npm run test:mcp`.
- Assertions/tolerancias: cada lectura MCP se limita a
  `maxResourceReadBytes`; el artefacto se trata como capability opaca y la
  lectura owner-bound interna rechaza otro workspace. Las dependencias son
  archivos locales dentro del root canónico, se copian con SHA-256, sus URIs
  se reescriben a `assets/`, y fuente/dependencias/bundle/manifest se
  revalidan antes de publicar.
- Resultado: T22–T25 completadas. `document_render_preview` devuelve un
  artefacto con URI opaca, hash y tamaño. Los templates MCP sirven el primer
  chunk o un chunk posterior sin enumerar artifacts ni cargar el archivo
  completo. El bundle nativo genera `input.svg`, `assets/` y `manifest.json`;
  rechaza referencias remotas, absolutas, inexistentes, fuera del workspace o
  mayores al límite configurado. Un segundo recheck del commit detecta writers
  externos de source/destino antes del rename, y `assertCurrent` detecta un
  cambio de dependencia antes de publicación.

### Mini-puerta F02-WP04

  source/dependencia/destino. Las pruebas preexistentes mantienen el ceiling

- Evidencia: `npm test -- --run tests/unit/storage.test.ts` (16/16),
  `npm run check` (16 archivos, 80 pruebas correctas y 1 omitida) y
  `npm run test:mcp` (stdio moderno y legacy, incluyendo lectura de resource

- Archivos: `src/storage/artifacts.ts`, `src/storage/native-input.ts`,

  `src/server/index.ts`, `tests/unit/storage.test.ts`,
  `scripts/test-mcp.mjs`, el plan y este informe.
- No se adelantaron APIs de F03. El siguiente WP lógico es `F03-WP01`
  (distinción de bounds geométricos/visuales y corpus de coordenadas).

## Seguimiento de puerta F02-G09 (2026-08-30)

- Se corrigieron los cinco contratos MCP de importación SVG, SVGZ, EPS/PS,
  EMF y PDF: `sanitizeMode` acepta exclusivamente `strict` o
  `preserve-local`. `trusted` queda reservado para la configuración de
  arranque y proveedores internos, nunca para una solicitud de cliente.
- El smoke test stdio intenta `document_import_svg` con `trusted` y exige un
  error sin que exista el output solicitado; por tanto la validación ocurre
  antes de resolver rutas, leer el documento o publicar artefactos.
- El mismo rechazo emite `sanitize_mode_trusted_rejected`: un evento fijo con
  componente, política y resultado, sin rutas, documento, workspace ni valor
  de cliente. La prueba unitaria fija ese payload y la puerta F02-G09 queda
  cerrada con el smoke MCP.

## Seguimiento de puerta F02-G03 (2026-08-30)

- Alcance: convertir los fallos XML hostiles en errores acotados y estables,
  antes de que un documento pueda alcanzar Inkscape o una publicación.
- El corpus prueba de forma independiente DTD, entidad, CDATA, XML malformado,
  raíz no SVG, bytes por encima del máximo, elementos por encima del máximo y
  anidamiento más profundo que 256. El caso profundo eleva únicamente su tope
  de elementos para comprobar el límite de nesting real.
- `@xmldom/xmldom` envolvía algunos `onError` en su `ParseError` interno. El
  sanitizador ahora normaliza cualquier fallo del parser a
  `SvgSecurityError("Malformed SVG")`, sin incluir mensaje de parser,
  fragmentos ni contenido del documento.
- El smoke MCP escribe un SVG con DTD, exige `isError` con diagnóstico DTD y
  confirma que no existe el output solicitado. Verificación: corpus focalizado
  14/14, `npm run check` (287 pruebas correctas, 1 omitida) y `npm run
test:mcp` por stdio. F02-G03 queda cerrada.

## Seguimiento de puerta F02-G04 (2026-08-30)

- Alcance: completar la evidencia de concurrencia sobre el store real, además
  de las pruebas ya existentes de revisiones stale, `ENOSPC`, staging y locks.
- Dos llamadas simultáneas a `AtomicFileStore.commit` con la misma revisión de
  source y output compiten por el lock canónico: exactamente una publica y
  conserva backup del contenido original; la otra recibe
  `RevisionConflictError` al revalidar el output bajo el lock.
- Un lote con dos outputs ya existentes fuerza fallo en el segundo `rename`.
  El primer output publicado se restaura desde su backup y el segundo nunca
  cambia; tampoco quedan temporales de Inkscape MCP. Los casos anteriores
  cubren análogamente un lote de outputs nuevos, sidecar sin revisión, writer
  externo y fuente que cambia durante staging.
- Verificación: `npm test -- --run tests/unit/storage.test.ts
tests/unit/runner.test.ts` (38/38) y `npm run check` (289 pruebas correctas,
  1 omitida). F02-G04 queda cerrada.
