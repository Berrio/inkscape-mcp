# F01 — Configuración, doctor, discovery y runner

## F01-WP01

- Objetivo verificable: disponer de configuración segura, determinista y redactable antes de abrir workspaces o iniciar procesos.
- Prerrequisitos/puertas: F00 cerrado.
- Interfaces disponibles: `loadConfig`, `loadConfigFromCli`, `parseConfigFlags`, `assertDocumentWorkspace` y `redactConfig`.
- Archivos/artefactos esperados: schema Zod, loader JSON/env/flags, configuración redactada, documentación y fixtures de config.
- No-objetivos: ejecutar Inkscape, arrancar un servidor MCP o acceder a documentos.

### Decisiones y contratos

- Precedencia: flags > entorno allowlisted > JSON > defaults.
- `workspaceRoots` se expresa en config administrativa. Las tools no recibirán rutas absolutas.
- `doctor` puede cargar config sin roots y reportar `workspaceReady: false`; `assertDocumentWorkspace` impide el uso posterior de document tools sin root.
- HTTP está restringido a `127.0.0.1` y auth `required`, aun cuando no se implemente el handler hasta F10.
- Paths de workspaces, scratch y ejecutable se sustituyen por estados `configured` en logs/resultados.

### Verificación ejecutada

```powershell
npm run check
```

- 11 pruebas correctas: defaults, precedence, roots ausentes, invalidación Zod, límites, flags allowlisted, JSON válido/malformado/desconocido, HTTP local y redacción.
- Formato, lint, TypeScript estricto y build correctos.

### Resultado

`F01-WP01` está cerrado. El siguiente work package permitido es `F01-WP02` (runner de procesos).

## F01-WP02

- Objetivo verificable: ejecutar únicamente procesos internos validados, de forma limitada, cancelable y sin procesos huérfanos normales.
- Prerrequisitos/puertas: `F01-WP01` cerrado.
- Interfaces disponibles: `ProcessRunner`, `AsyncSemaphore`, `ProcessTracker`, `buildMinimalEnvironment` y fake Inkscape.
- No-objetivos: aceptar paths/flags públicos, ejecutar Inkscape real o manipular documentos.

### Decisiones y contratos

- El runner siempre usa `shell: false`; los metacaracteres permanecen dentro de un único argumento.
- Stdout y stderr tienen presupuestos distintos. Al superarlos se conserva solo el prefijo acotado y se termina el proceso.
- Windows usa `taskkill /T /F` para el PID creado por el runner; la prueba cubre un nieto normal. El límite de procesos desacoplados se mantiene explícito.

### Verificación ejecutada

```powershell
npm run check
```

- 22 pruebas correctas en total.
- El runner cubre éxito, error no cero, stdout/stderr enormes, timeout, AbortSignal, señal inicial ignorada, artifact parcial, semaphore, rutas Unicode/metacarácteres y árbol Windows.
- Formato, lint, typecheck y build correctos.

### Resultado

`F01-WP02` está cerrado. El siguiente work package permitido es `F01-WP03` (discovery de Inkscape).

## F01-WP03

- Objetivo verificable: localizar instalaciones de Inkscape sin exponer ejecutables al cliente y confirmar que son CLI utilizables.
- Prerrequisitos/puertas: `F01-WP02` cerrado.
- Interfaces disponibles: `locateInkscape`, proveedores de candidatos y `probeInkscapeCandidate`.
- No-objetivos: anunciar capabilities, ejecutar exportaciones o iniciar MCP.

### Decisiones y contratos

- Los proveedores son independientes: ruta de arranque, `PATH`, ubicaciones estándar, registro/App Paths y AppX/MSIX.
- Un candidato se resuelve canónicamente, debe ser archivo, se deduplica y luego se prueba con `--app-id-tag` y `--version` mediante el runner central.
- El proveedor MSIX deriva candidatos desde `InstallLocation`; no codifica la versión del paquete.
- `PATH` no contamina doctor con rechazos de todos sus directorios inexistentes. Las rutas configuradas o derivadas de instaladores sí dejan evidencia diagnóstica.

### Verificación ejecutada

```powershell
npm run check
$env:RUN_INKSCAPE_INTEGRATION='1'; npm run test:integration
```

- 27 pruebas unitarias correctas; una integración queda omitida por defecto para no requerir Inkscape en CI.
- La integración local de Windows pasó y encontró la instalación MSIX; la sonda devolvió `Inkscape 1.4.4 (dcaf3e7, 2026-05-05)`.
- Se cubren rutas inexistentes, ejecutable falso, salida no reconocida, registro ajeno filtrado, instalaciones MSIX derivadas y deduplicación.

### Resultado

`F01-WP03` está cerrado. El siguiente work package permitido es `F01-WP04` (capabilities y doctor).

## F01-WP04

- `--doctor` humano y `--doctor --json` descubren la instalación, validan la versión, recogen flags/input types/actions y ejecutan una exportación PNG de 1×1 en scratch temporal.
- La ejecución local pasó: MSIX 1.4.4, 189 acciones, 55 tipos de entrada, 69 opciones y sonda PNG correcta; `workspaceReady` queda `false` hasta que se configure un root.
- El snapshot tiene TTL de cinco minutos y huella SHA-256/metadata de ejecutable, perfil, data dirs, extensiones/INX y helpers. La clave cambia si cualquiera de esas entradas cambia.
- Las 189 acciones son evidencia observada con origen `unknown`: el modelo diferencia ese estado de core/extensión, flags `absent` y capabilities `experimental`, pero no inventa una clasificación. La puerta de ≥1000 acciones no se satisface para esta compilación.

### Resultado

`F01-WP04` está cerrado. El siguiente work package permitido es `F01-WP05` (servidor MCP y `inkscape_status`).
