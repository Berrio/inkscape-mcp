# F09 — Contrato MCP, progreso y jobs

## F09-WP01 (completado el 2026-08-30)

- Objetivo verificable: fijar el contrato base de `buildServer()` por stdio
  antes de ampliar resources, progreso o jobs persistentes.
- Resultado: el constructor de `McpServer` declara instrucciones compactas que
  dirigen a inspeccionar primero, usar workspace/path relativos explícitos,
  aportar revisiones para mutar/overwrite y consultar capabilities. No añade
  una ruta de documento activa ni inputs sin tipo.
- `test:f09-wp01` inicia dos procesos nuevos mediante `StdioClientTransport`
  con la negociación MCP fijada en `2026-07-28`. Ambos publican el mismo
  catálogo completo (más de 80 tools únicos y tipados), incluyendo los
  flujos de workspace, diseño, imágenes, importación y exportación.
- El smoke comprueba que un `document_inspect` sin workspace autorizado y un
  campo desconocido en `inkscape_status` devuelven `isError`; por tanto no se
  selecciona un documento implícito ni se ignoran inputs no tipados. El logger
  permanece en stderr, por lo que stdout queda para framing MCP. También
  inicia un cliente raw y fija una respuesta JSON-RPC de error para parámetros
  MCP inválidos.
- La regresión de notificaciones de progreso queda pendiente de F09-WP03
  (F09-T12/T13); este WP no adelanta ese contrato push. Sí inicia una
  exportación PNG real como job y fija que `job_get` expone una etapa
  monotónica `rendering`/`publishing` durante o después de la ejecución.
- La regresión fija que todo tool anuncia una intención booleana válida y un
  schema de salida cerrado. También recorre las uniones de salida y conserva
  las anotaciones y campos públicos de status, workspace, inspección, creación,
  preview, export batch y jobs.
- Verificación: `npm run test:f09-wp01` y `npm run check` correctos (75
  archivos de prueba, 299 pruebas correctas y una omitida).

## F09-WP02 (completado el 2026-08-30)

- Resources estáticos: `inkscape://server/capabilities`, los presets de página
  y los presets de exportación. Su contenido se limita a datos de planificación
  redaccionados y no expone roots, ejecutables ni documentos.
- `document_inspect` emite tres capabilities opacas, no enumerables y con TTL:
  metadata, summary y SVG explícitamente solicitado. El registro conserva la
  ruta sólo en memoria, revalida SHA-256 en cada lectura y rechaza un SVG que
  exceda `maxResourceReadBytes`.
- Los resources de artifact/chunk conservan el contrato acotado existente. La
  nueva tool `artifact_read_chunk` exige `workspaceId` dueño, ID opaco, offset
  y longitud limitados; devuelve el hash, tamaño y un solo chunk base64.
- Un batch entregado como job devuelve el URI opaco del manifest. Este resource
  sólo se resuelve al completar el job y conserva el owner internamente.
- Se registraron los prompts sin efectos `audit_document`, `prepare_web_export`,
  `prepare_print_pdf`, `create_asset_pack` y `optimize_svg`; cada uno devuelve
  una receta de texto visible y argumentos cerrados.
- `tests/unit/document-resources.test.ts` cubre URI opaca, owner ajeno, TTL,
  revisión stale y límite. `test:f09-wp02` cubre resources/list, templates,
  no enumeración de documentos, redacción, prompts, chunks owner-bound y un
  manifest real de job por stdio.
- Verificación: `npm run test:f09-wp02` y `npm run check` correctos (76
  archivos de prueba, 301 pruebas correctas y una omitida).

## F09-WP03 (completado el 2026-08-30)

- Alcance: F09-T12–T17. El handler de `document_export_batch` recibe el
  contexto moderno MCP y toma el `progressToken` del sobre de request; conserva
  compatibilidad con `_meta` legado sin abrir ningún campo de cliente adicional.
- Progreso: las exportaciones síncronas emiten seis etapas ordenadas
  (`validated`, `staging`, `rendering`, `verifying`, `publishing`, `completed`)
  con `total: 6`. Mensajes de variante están restringidos a texto seguro y las
  repeticiones se coalescen durante 250 ms. El smoke por stdio recibe las seis
  posiciones sin ruta de workspace ni nombre de documento.
- Cancelación: la señal MCP llega al renderer y los jobs pasan su señal al
  mismo pipeline. Los jobs se restringen a `all_or_nothing`; antes de publicar
  se pueden cancelar sin dejar output. Al iniciar el commit atómico se cierra
  la cancelación: el resultado queda `completed` si ya se publicó, evitando
  afirmar erróneamente que un archivo existente fue cancelado.
- Ciclo de vida: `JobStore` conserva owner, TTL terminal, cleanup callback y
  purga de entradas expiradas. Un job fallido o cancelado borra inmediatamente
  su capability de manifiesto; las capabilities de otros jobs permanecen
  inaccesibles y sin alteración.
- Pruebas: `tests/unit/jobs.test.ts` cubre expiry, callback terminal y carrera
  publication/cancel; `tests/unit/document-resources.test.ts` cubre borrar sólo
  el manifest del job cancelado. `test:f09-wp03` ejecuta ambos y un cliente
  `StdioClientTransport` fijado a `2026-07-28`, comprobando progreso real,
  manifest cancelado no legible y rechazo de job `best_effort`.
- Verificación: `npm run test:f09-wp03` correcto; `npm run check` correcto
  (76 archivos de prueba correctos, uno omitido; 305 pruebas correctas y una
  omitida).

## F09-WP04 (completado el 2026-08-30)

- Alcance: F09-T18–T23. Se añadió una prueba del handler MCP moderno en el
  mismo proceso con un listener loopback efímero y cliente SDK v2 pinned a
  `2026-07-28`; afirma tanto versión como era `modern` antes de cerrar el
  listener. No habilita el transporte HTTP de producto.
- Compatibilidad: `InMemoryTransport` prueba de forma independiente el
  protocolo legacy `2025-11-25`; el smoke stdio ejecuta moderno, legacy y una
  sonda pinned `2099-01-01` que recibe el error tipado de versión no soportada.
  No se infiere compatibilidad sólo por usar SDK v2.
- Contrato: la huella SHA-256 fija el catálogo ordenado completo, incluyendo
  nombres, descripciones, annotations y schemas de entrada/salida. Las pruebas
  verifican además texto compatible/`structuredContent`, error recuperable,
  imagen PNG inline y `resource_link` opaco para un preview que supera el
  límite inline.
- Inspector: `scripts/test-f09-inspector.mjs` usa el Inspector 2.3.0 presente
  en el lockfile, invoca su CLI por stdio contra `dist/cli.js` y valida
  `tools/list` sin descargar paquetes ni crear un catálogo persistente.
- Verificación: `npm run test:f09-wp04` y `npm run check` pasan. El primero
  reúne test in-process, stdio moderno/legacy, resources y Inspector oficial.

## F09-WP05 (completado el 2026-08-30)

- Alcance: F09-T24–T26. Stdio mantiene diagnósticos JSON redaccionados sólo por
  stderr; stdout permanece reservado para framing MCP y el código no usa el
  logging MCP deprecado.
- `InternalTelemetry` es estrictamente process-local: sus únicos nombres son
  `stdio_listening` y `stdio_error`; registra contador, duración y resultado.
  No acepta labels/payloads, no exporta datos, no persiste y no se expone por
  tools/resources/notifications, por lo que paths, SVG, documentos, tokens y
  errores crudos no pueden cruzar su API.
- El logger inicia un span sólo al escribir su evento stderr y lo cierra con
  resultado `ok`/`error`; una ventana de 100 spans evita crecimiento sin límite.
- Verificación: `npm run test:f09-wp05` cubre redacción, contador, resultado y
  límite; `npm run check` pasa con la suite completa.
